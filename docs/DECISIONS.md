## D-019 (OPEN): how to get past the 512 KB single-file limit

Context: ai_autoreply is 521299 B of 524288 B (2989 B free, 9189 lines). Features keep being added, and each release already needed a trimming commit (D-016). The limit lives in `tools/build_index.py` (`MAX_PLUGIN_BYTES`) and README rules; the app side (download size check against the index `size`, loader that runs exactly one file) is not in this repo and its own limit is `unknown`.

Options:

1. **Multi-file plugin support** (app + index builder + signing hashes). A plugin becomes a bundle: main `.plugin` plus extra modules (or a zip); `build_index.py` hashes and lists every file (sha256 and size per file, and an overall limit), the signed index covers them, the app downloads all files atomically, verifies each hash and imports the modules. Pros: removes the ceiling, allows splitting ai_autoreply (prompting, settings pages, memory, timing) and testing the parts, keeps one install/one permission set. Cons: needs an app release (loader, updater, rollback of a set of files), a new `schema`/capability flag so old apps keep seeing single-file plugins, new validation rules (no sub-directories today: `ALLOWED_FILES`), more attack surface to review.
2. **Two plugins** (for example core reply engine and a "pages/settings" or "memory" plugin). Pros: works with today's app and index. Cons: two installs and permission prompts, shared settings and state need a bridge that the plugin API does not have (plugin settings are per plugin), version skew between the two, worse UX.
3. **Trimming** (continue D-016). Pros: no cross-repo work. Cons: already used up (comments and docstrings are gone), each trim costs review time and risks regressions, no room for new features; this only postpones the decision.
4. **Server offload** (move prompt building, memory or heavy logic to a server such as the existing Neon/AI service). Pros: shrinks the plugin and eases updates. Cons: privacy and trust implications (chat content leaves the phone), network dependency, hosting and cost, offline behaviour, and a server API to maintain; conflicts with the opt-in privacy stance in D-008.

Recommendation: **option 1, multi-file plugin support.** It is the only option that removes the cause instead of the symptom, keeps everything local and under one permission set, and the repo-side change (builder, index schema, hashes) is small compared with the app side. Do it as a backwards-compatible index extension, keep single-file plugins unchanged, and until it ships freeze ai_autoreply features that do not fit in the 2989 B left.

Open questions: the app's own size/format limits (`unknown`); who changes the app and when (`unknown`); signing/format design (per-file hashes inside the already signed `index.json` is the obvious route, not yet designed).
